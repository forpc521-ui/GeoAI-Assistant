# 北京在线道路与建筑物分析

> 实验路径（历史记录）：公共接口在本机持续超时，未完成真实在线闭环，当前主应用已移除此导航。仅保留独立 online_app.py 供排查；当前推荐 [海淀区本地数据](HaidianData.md)，不要按下文旧主应用入口寻找在线选项。

## 本机体验

无需上传GeoJSON、无需API密钥。启动现有环境：

```powershell
Set-Location 'D:\GeoAI-Assistant'
& '.\venv\Scripts\python.exe' -m streamlit run '.\04_Code\online_app.py' --server.address 127.0.0.1 --server.port 8502
```

打开 http://localhost:8502 。也可以在原app.py的自然语言空间分析中，选择“北京在线数据（无需上传）”。

1. 输入完整道路名称，点击搜索（不是自动补全，不发送逐字请求）。
2. 确认OSM路段编号、坐标范围和道路预览。共享节点的路段组成一个候选，不连通的同名路段不自动合并；平行道路也可能分开，候选不保证是整条道路。当前没有行政区地址反查，不能冒充已完成区县级消歧。
3. 选择1–1000米距离，确认获取建筑物并分析。
4. 查看统计、地图、CSV和GeoJSON；任务记录中下载ZIP或用当时的输入快照复现，不重新请求在线服务。

## 数据来源与边界

- 数据：© OpenStreetMap contributors，许可说明：https://www.openstreetmap.org/copyright 。通过Overpass API查询OSM北京市行政区内具有完整匹配name和highway标签的道路。
- 默认端点：https://overpass-api.de/api/interpreter 。管理员可在启动前通过OVERPASS_API_URL设置其他HTTPS Overpass服务；服务许可和使用限制应另外确认，不会自动向多个服务重试。
- 单进程串行请求，至少2秒间隔；查询超时25秒、网络超时40秒；响应上限20MB。缓存1小时，保留最多128个查询结果，位于被Git忽略的03_Data/online_cache。
- 道路候选不超过2000段，所选路段总长度不超过20公里；建筑物查询包围范围不超过150平方公里。超限明确拒绝，建议缩小路段或距离。
- 建筑物查询范围为路段缓冲距离再扩100米后的包围框；返回的轮廓经过原有EPSG:32650计算。关系面组装外环与内环，同一关系的成员建筑面不重复计数；无法处理的建筑对象显示排除数量。
- 查询范围、OSM底库时间、获取时间、接口、查询表达式、响应摘要、道路OSM编号与许可链接保存在任务manifest的online_source中，复现任务继承来源。原始输入GeoJSON及结果进入现有哈希校验任务包。
- OSM不是完整建筑物普查。包围框查询还可能遗漏没有节点落入范围的跨界大面，几何不完整对象可能被排除。不能承诺“所有道路”或完整建筑数量。返回为空时不生成成功任务，不说“周围没有建筑物”。
- “范围外”和占比的分母仅为本次在线查询返回的有效建筑物；不同查询框的占比不能直接当作同一总体比较。道路确认、数据查询与GIS计算均不调用DeepSeek。

## 验证与当前限制（2026-11-10）

- 原39项回归与新增6项在线模块测试，共45项通过；原300/500/1000米基线仍为53/105/191。
- 新测试覆盖：同名不连通路段隔离、查询转义、关系面与孔洞去重、空数据/距离限制、失败响应拒绝缓存、快照计算和离线复现。
- Streamlit测试框架验证了页面加载、模拟候选搜索和搜索失败清除旧候选；这不是公共接口真实成功证据。
- 本机对两个公共Overpass端点的真实请求均超时。因此真实道路搜索→在线建筑物获取→实际计算尚未验收通过；没有填入假数据或将测试夹具当作线上结果。
- 原GitHub Pages仍是合成数据体验版，不能运行Python计算服务；没有将这一入口发布成公网后端。当前独立入口适合本机验证，任务记录使用本地共享目录。对外部署前还需会话隔离、访问与查询限额及可达数据服务，不能直接将共享任务目录对公网开放。

代码实现已具备在线请求与错误处理，但本机网络/数据服务可达性恢复后，仍需实际完成至少一个北京道路任务，核验返回来源、地图、导出和复现，才能宣布在线闭环验收通过。

## 搜索超时诊断（2026-11-10补充）

在页面展开“在线数据连接设置”，选择服务及连接方式，再点击“快速检测当前服务”。微型查询跳过缓存，10秒超时；它通过才值得继续尝试真实道路查询。默认保持系统代理设置；“仅本次请求直连”只为本应用构造无代理请求，不修改系统配置或关闭证书验证。

本机检查发现Python使用Windows本机代理127.0.0.1:7897。主服务、旧Kumi域名、新Private.coffee域名经默认代理的微型请求均超时。直连主服务微型GET返回HTTP502，直连Private.coffee仍超时；另一公开端点直连遇到HTTPS握手或证书失败。因此不是仅靠增加道路查询超时就能解决；未取得任何真实道路数据成功证据。

界面现在区分HTTP429限流、502/503网关与服务异常、504服务端超时、403拒绝、连接/代理超时及HTTPS问题。旧Kumi域名已由服务方说明改用overpass.private.coffee，页面使用新域名作为手动备用选项。参考：https://overpass.private.coffee/index.html 。

若直连检测成功，可按该模式继续搜索；若系统代理模式检测失败，需在用户自己的代理软件中核验线路是否可访问所选Overpass域名。若两种方式均失败，需要可达的合规数据服务或部署环境，无法由GIS算法修复公网路由/服务异常。不要反复重试，也不要关闭TLS证书校验。
