# GeoAI Assistant：方案选型与AI指标

> 作品集定位：采用“受约束参数解析＋确定性GIS计算”的任务工作流，另设RAG知识问答。当前具备模型接入和固定流程工具执行，没有自主多步规划或多Agent协作。本节基于现有实现解释选型；未开展所有候选方案的同条件实验，不将推理判断写成实测优势。

## 1. 选型结论：按任务分工，而非堆叠AI能力

项目需要解决两个不同问题：一是帮助用户表达道路、距离和建筑物筛选需求；二是解释GIS知识和操作方法。前者输出必须能被校验并进入空间计算，后者需要资料依据。

因此将系统拆成两条路径：

```text
空间任务：指令 → 本地规则或DeepSeek提参 → 程序校验 → GIS计算
                                                    ↓
                                      地图/统计/明细/导出/历史复现

知识问题：问题 → 本地向量检索 → 相关资料片段 → DeepSeek回答及来源展示
```

**核心判断：**标准句式可用规则完成，不必让模型参与；开放表达可探索用模型减少句式限制，但需要评测证明；缓冲区、距离、相交判断和计数交给GIS引擎；需要知识解释时才使用RAG。AI不直接给出空间统计结果。

## 2. 候选方案对比

API调用、RAG、微调、Agent并不是互斥选项：API是模型接入方式，RAG补充外部资料，微调改变模型参数，Agent涉及任务决策和工具编排；多模态/CV则对应输入或感知能力。本项目按具体任务选择组合。

| 方案 | 能解决什么 | 当前项目的取舍 | 决策理由与后续条件 |
|---|---|---|---|
| 直接调用大模型，生成最终答案 | 快速理解问题、组织文字 | 不用于直接生成建筑数量、距离与几何；采用API做参数提取及问答生成 | 缺少实际图层计算时无法提供可核验结果；结构化JSON仍要经程序校验 |
| RAG | 将本地资料作为回答上下文，展示参考依据 | 用于GIS知识问答，不用于替代空间计算 | 知识来源可追溯，资料更新可重建索引；仍可能漏检或产生无依据内容，效果须单独验证 |
| 微调 | 根据标注样本调整任务行为或表达风格 | 当前不采用 | 尚无独立标注训练集及必要性证据；先评估提示、校验与检索瓶颈。若固定错误在留出集持续存在，再比较微调收益与数据/运维成本 |
| 自主Agent/多Agent | 动态规划步骤、选择工具并迭代执行 | 当前采用预定义工作流，不引入自主多步规划 | 单路、单距任务步骤已确定。自主规划增加状态、调用和验收复杂度；有真实多步骤需求后再评估 |
| 多模态模型 | 理解地图截图、图纸或其他非文本输入 | 当前不采用 | 当前输入是文本和已有矢量数据，没有图片理解需求；增加模态无法弥补数据覆盖或GIS计算问题 |
| 传统CV/ML | 从影像识别建筑、分类或预测 | 当前不采用；不把GIS几何运算称作ML | 已有建筑物多边形，无需影像检测；若转为从遥感影像提取建筑，需另建数据标注、检测评测和误差传递方案 |
| 规则/参数表单＋GIS | 处理明确任务，执行可复核计算 | 规则＋GIS是当前已验证主线；表单是可选改进，尚未新增 | 无模型请求成本，便于校验；代价是自然表达覆盖有限，应把失败与泛化问题如实展示 |

RAG与微调分别解决不同问题，必要时可以组合，不能用“RAG永远比微调好”作结论。[AWS技术比较](https://docs.aws.amazon.com/prescriptive-guidance/latest/retrieval-augmented-generation-options/rag-vs-fine-tuning.html)区分了检索上下文与模型适配；对本项目而言，优先检索和校验是基于现有数据与任务约束的判断。流程固定时采用工作流、需要动态决策时再考虑Agent，也符合[Anthropic对两者的架构区分](https://www.anthropic.com/research/building-effective-agents)。

## 3. 为什么采用当前组合

### 3.1 空间主线：API只负责提参，GIS负责结果

模型通过JSON提取道路、距离、操作三个字段。程序检查字段集合、道路白名单、距离范围和原文一致性，且拦截已知不支持意图。只有校验通过才捕获输入并执行计算，不运行模型生成的代码。

这使结果能够对应具体输入、参数与计算过程，支持CSV、GeoJSON和历史重算。限制是结构校验不能识别所有语义遗漏；固定提示词和白名单也不代表未知请求绝不会被误放行。

用户手动选择规则或DeepSeek；当前没有“规则失败后自动切模型”，也没有自主路由。没有API时仍可完整演示已支持的空间流程。

### 3.2 知识主线：RAG提供依据，生成模型组织解释

使用BAAI/bge-small-zh-v1.5进行向量表示，FAISS检索至多3个片段，再交给DeepSeek生成回答，并展示片段来源及相似度。资料可通过更新文档及索引维护，无需为每次资料变更训练模型。

但“检索到了片段”不等于“回答全部有依据”。现已建立开发者标注的检索基线，并完成回答级AI证据核对；尚无独立人工相关性标注及声明级事实审核，也未做有无RAG的同题对照，因此不能称RAG降低了某个百分比的幻觉。

### 3.3 当前模型选择的证据边界

项目沿用已有DeepSeek API集成，使用deepseek-chat接口名，便于保持现有代码和环境。没有进行不同模型的同集A/B测试，不能声称DeepSeek最便宜、最快或GIS能力最强；API接口名也不等于已冻结的服务端模型版本。

## 4. 约束条件与对应设计

| 约束 | 已有设计 | 尚需验证/接受的代价 |
|---|---|---|
| 成本 | 本地规则不请求模型；模型提参max_tokens=300，问答max_tokens=1200；自然语言解析不自动重试 | 输出限制不等于实际账单；应记录输入/输出usage、请求和失败，按当时价格计算“总API费用/成功闭环任务”，本轮未实测 |
| 延迟 | 规则路径避免模型网络等待；输入缓存与知识资源缓存；自然语言解析超时30秒 | 30秒是请求超时配置，不是响应时延成绩或严格总等待上限；在线API、冷启动、前端渲染需分开测 |
| 数据安全 | 图层计算与历史文件在本地；.env不进入任务ZIP；模型接收指令/道路名或问答检索片段，不负责几何运算 | 指令、道路名与片段仍会发送给外部API；本地任务包含几何及路径。现有接入不适合直接处理未获授权外传的涉密资料 |
| 算力与维护 | 不本地部署或训练大语言模型；本地运行向量模型、FAISS及GIS，复用现有环境 | 未做CPU/GPU/内存对比或容量压测；不能声称“无需GPU且达到生产性能”。大规模数据需另测 |
| 幻觉与错误 | 用GIS计算数值，解析参数前后校验，问答提示依据资料且展示来源；失败提示改写或选规则 | 提示词不能保证无幻觉；参数错误放行和问答无依据内容均需专项评测，尚无校准置信度或自动转人工机制 |
| 可追溯 | 保存输入、参数、结果、环境与代码摘要；快照复现跳过模型 | 复现验证GIS结果，不代表模型回答可复现；摘要不是防篡改签名 |

## 最新实测指标（2026-11-11）

本地完整项目完成20道RAG问题（16道可回答、4道资料不足/越界）与10条空间指令的开发评测。公开Demo仍为合成样本和本地知识检索，不能将这些指标归到公开前端。

| 指标 | 实测结果 | 边界 |
|---|---|---|
| Recall@3（逐题平均） | 96.88% | 16道可回答题；标准为独立充分回答问题的证据片段 |
| Precision@3（逐题平均） | 35.42%（17/48） | 本套窄口径标注的理论上限为37.50%，不能解释为只有35%的内容正确 |
| 回答级无依据扩展率（幻觉代理） | 5%（1/20） | AI证据核对，未经独立人工复核；不是外部事实错误率，严格事实幻觉率与声明级幻觉率仍未测 |
| 越界/资料不足题正确拒答 | 4/4 | 小样本，不承诺长期100% |
| 空间指令解析 | DeepSeek 10/10；本地规则8/10 | 同一批6条有效和4条异常开发指令，经过产品校验，不是基础模型通用准确率 |

召回证据片段共18份，命中17份；微平均召回17/18=94.44%，与逐题平均96.88%不可混用。20次RAG请求均成功，但API成功不代表回答全对。检索固定Top3且多数题只有一个标准片段，因此精确率受到题集设计上限影响。

R14将“不良地质区域”扩展为检索片段未明确给出的“滑坡、崩塌”，记为无依据扩展，但未判定其常识本身错误。R09有英文拼写错误，另计文字质量问题。小样本、开发者标注和单一AI评审使结论受限，不能把5%写成经人工验证的事实幻觉率。

证据：[最新评测报告](../ai_quality_20261111/report.md)、[逐题分数](../ai_quality_20261111/case_metrics.csv)、[核对说明](../ai_quality_20261111/grounding_review.json)。2026-10-18的39项工程回归及30条旧指令评测保留为历史基线，不与本轮混算。

## 5. 关键AI指标：定义、当前结果与测量方式

检索质量、回答质量和任务执行质量分别评估，不把39项工程回归通过当成模型准确率。[Microsoft的RAG评测说明](https://learn.microsoft.com/en-my/azure/ai-foundry/concepts/evaluation-evaluators/rag-evaluators?view=foundry)同样区分检索过程与回答的依据性、完整性；以下公式为本项目采用的操作定义，并非该文档提供的统一验收阈值。

### 5.1 用户关心的六类指标

| 指标 | 本项目定义 | 当前结果 | 如何测量及避免误读 |
|---|---|---|---|
| 召回率Recall@K | 对有资料支持的问题：Top K命中的相关片段数 / 人工标注的全部相关片段数 | 96.88%（16题，2026-11-11） | 小知识库逐问标注相关片段；K=min(3,索引片段数)。按问题报告并宏平均；没有相关资料的问题单列拒答/不足说明，不强行算Recall |
| 精确率Precision@K | Top K中相关片段数 / 实际返回的片段数 | 35.42%（17/48；本题集上限37.50%） | 与Recall使用同一标注和K；片段相关不代表最终回答正确。无返回结果单列，不跳过失败以美化总体表现 |
| 幻觉代理/无依据扩展率 | 至少一条无检索依据领域扩展的回答数 / 成功回答数 | 回答级5%（1/20）；声明级与严格事实幻觉率未测 | AI核对未独立人工复核；完整口径见最新评测报告，不能将依据性直接当作现实真假 |
| 响应时延 | 各链路实际计时，报告样本量、P50/P95和范围 | 本地成功业务n=12：P50=425.36ms、P95=786.41ms | 包含解析、计算保存、重载及ZIP；不含冷启动、浏览器渲染、复现，不是在线模型时延。在线需补提交到结果可见的端到端时间，问答可另测首字与完整回答 |
| 吞吐量 | 在固定硬件/数据/并发下，通过正确性及延迟要求的成功任务数 / 测试窗口秒数 | 未测 | 逐档并发测量，报告窗口、并发、成功数、错误率、延迟及API限流。评测器并行3个请求不是3QPS；不能用1/P50推算系统吞吐 |
| 用户满意度CSAT | 完成预设任务后，5分制中评分4或5的有效答卷数 / 全部有效答卷数 | 未测 | 报告参与者、任务、人数、答卷数、评分分布和未响应数；与完成率、帮助次数一起解释。不能用测试通过率或下载数替代满意度 |

召回率与精确率在这里首先指RAG片段检索，不是建筑物检测，也不是任务参数正确率。当前已有空间参考核对可支持“计算结果与参考一致”的结论，不可据此宣布RAG Recall或模型Precision达到100%。

### 5.2 空间任务必须补充的应用指标

| 指标 | 定义 | 2026-10-18本地规则基线 |
|---|---|---|
| 参数全对率 | 道路、距离、操作全部正确 / 全部有效指令 | 12/20，60% |
| 异常处理正确率 | 对异常明确拒绝或澄清 / 全部异常指令 | 10/10；API故障不算正确拒绝 |
| 端到端闭环通过率 | 参数、计算、保存、重载、ZIP及快照复现均通过 / 全部有效指令 | 12/20，60% |
| 结果一致性 | 已执行任务的关键ID、几何、距离、导出与参考符合 | 空间与复现核验各12/12，为条件指标 |

原30条开发用例中，标准表达12/12、同义改写0/8、异常10/10。以上为2026-10-18历史基线；2026-11-11的DeepSeek与RAG实测见上方最新指标，不将本地规则成绩写成模型效果。39项回归是工程测试数量，不是39名用户或39条独立模型请求。

## 6. 下一轮怎样验证选型是否成立

1. **规则与模型提参对照：**冻结独立有效/异常/混合意图集，两种模式用相同输入和标签，比较参数全对、闭环通过、错误放行、端到端耗时及每成功任务成本。保留解析失败和API故障，不从分母剔除。
2. **RAG与直接问答对照：**同一模型、同一问题及版本条件，分别提供和不提供检索上下文；由人工按冻结的依据、预期要点及事实项标签审核，比较无依据事实率、有效回答覆盖及耗时。不要预先写RAG必然胜出。
3. **真实用户验证：**让接近目标用户的参与者完成同任务，记录独立完成、结果理解、CSAT及手动GIS对照时间。使用成本和质量一起决定是否保留模型入口，不只展示好看的模型分数。
4. **升级条件：**先定位错误来源。召回不足先看资料、分块与检索；检索到但答错先看提示和依据约束；稳定行为偏差且有足够标注时再评估微调；只有任务需要动态选工具与多步规划时才考虑自主Agent。

以上是待执行的验证计划；PRD中新增门槛也属于拟定目标，不能在作品集中写成当前成绩。小样本的0次错误不意味着长期错误率为0。

## 7. 面试中如何解释这项决策

我的选型先按任务拆分：固定空间任务用规则或模型提取参数，再由GIS引擎计算；知识解释用RAG提供资料上下文。规则保留了无需API的完整路径，模型只在需要更灵活表达时提供可选能力。当前流程步骤确定，所以没有引入自主多步Agent；已有矢量数据，也不需要CV重新识别建筑。

我没有通过堆叠模型技术证明产品成立，而是分别建立参数、空间结果、导出复现和知识回答的验证口径。现有30条开发指令中，本地有效任务闭环为12/20，同义改写失败说明表达覆盖需要改进；本轮已完成小规模检索与模型链路评测，严格事实幻觉率、独立人工评审与真实用户满意度仍需验证。下一步是否采用更复杂方案，要看同条件质量、成本、延迟与用户任务收益。
